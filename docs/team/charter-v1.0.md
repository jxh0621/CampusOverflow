# CampusOverflow 团队章程 v1.0

## 1. 团队价值观

- **用户为先**：每一行代码都要回答"对学习者有什么帮助"
- **透明沟通**：问题尽早暴露，不隐瞒、不拖延
- **代码即文档**：好的命名和测试胜过注释
- **持续交付**：小步快跑，频繁集成，不留技术债过夜

## 3. 沟通约定

- 日常沟通：微信/飞书群
- 每日站会：每周一/三/五 课外时间，15分钟，三问：昨天完成什么、今天计划什么、遇到什么阻碍
- Sprint 计划会/评审会/回顾会：实验课时间
- 阻塞问题超过2小时未解决，立即在群里@对方

## 4. 开发规约

### 4.1 Git 流程
- 主分支：`main`（保护）→ `develop`（集成分支）→ `feature/<姓名>-<任务>`（个人开发分支）
- 不允许直接 push 到 main/develop
- 每个任务一个 feature 分支，完成后发 PR，至少一人 Review + LGTM 后合并
- Commit 信息格式：`<type>: <描述>`，type 为 feat/fix/docs/refactor/test/chore
- PR 标题格式：`[PB-XX] 简短描述`

### 4.2 代码规范
- 后端：遵循 Alibaba Java 开发手册，类名大驼峰，方法名小驼峰
- 前端：ESLint + Prettier 强制格式化
- 领域层不依赖 Spring/JPA（FF-1 架构约束）
- 提交前本地跑通：`mvn test -pl co-qa,co-reputation,co-discovery`

### 4.3 测试规约
- 新功能必须先写测试（红→绿→重构）
- 不修改已有测试断言
- 核心业务规则必须有单元测试覆盖
- PR 描述中附上测试通过截图或输出

## 5. DoR / DoD

### Definition of Ready（故事可进入 Sprint）
- 以"作为<角色>，我可以<功能>，以便<价值>"格式书写
- 有可验证的验收标准（Given/When/Then）
- 估算故事点 ≤ 8 点，超过则拆分

### Definition of Done（故事完成）
1. 代码经 PR 合入 develop，至少1名队友 Approve
2. 领域测试 + 应用层测试全部通过
3. ArchUnit 架构测试通过
4. CI 流水线绿灯
5. Swagger UI 可访问且接口可用
6. 无 console.log / TODO 遗留（tech-debt 除外）

- 任务分配不均：每日站会调整，PO 优先保障主链路
- Code Review 争议：以测试通过和架构约束为依据，不纠结风格
